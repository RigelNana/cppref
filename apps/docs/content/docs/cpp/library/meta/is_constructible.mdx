  <DeclarationDescription>
    {/* source:cpp-types-is-constructible:0001 */}
    1. If `T` is an object or reference type and the variable definition `T obj(std::declval<Args>()...);` is well-formed, provides the member constant `value` equal to `true`. In all other cases, `value` is `false`. For the purposes of this check, the variable definition is never interpreted as a function declaration, and the use of [`std::declval`](/docs/cpp/library/utility/declval) is not considered an [odr-use](/docs/cpp/language/basic_concepts/definition#ODR-use). [Access checks](/docs/cpp/language/classes/access) are performed as if from a context unrelated to `T` and any of the types in `Args`. Only the validity of the immediate context of the variable definition is considered.

    {/* source:cpp-types-is-constructible:0002 */}
    2. Same as (1), but the variable definition does not call any operation that is not trivial. For the purposes of this check, the call to [`std::declval`](/docs/cpp/library/utility/declval) is considered trivial.

    {/* source:cpp-types-is-constructible:0003 */}
    3. Same as (1), but the variable definition is `noexcept`.
  </DeclarationDescription>
</DeclarationDoc>

{/* source:cpp-types-is-constructible:0004 */}
If `T` or any type in the parameter pack `Args` is not a complete type, (possibly cv-qualified) `void`, or an array of unknown bound, the behavior is undefined.

{/* source:cpp-types-is-constructible:0005 */}
If an instantiation of a template above depends, directly or indirectly, on an incomplete type, and that instantiation could yield a different result if that type were hypothetically completed, the behavior is undefined.

{/* source:cpp-types-is-constructible:0006 */}
If the program adds specializations for any of the templates described on this page, the behavior is undefined.

### Notes

{/* source:cpp-types-is-constructible:0009 */}
In many implementations, `is_nothrow_constructible` also checks if the destructor throws because it is effectively `noexcept(T(arg))`. Same applies to `is_trivially_constructible`, which, in these implementations, also requires that the destructor is trivial: [GCC bug 51452](https://gcc.gnu.org/bugzilla/show_bug.cgi?id=51452) [LWG issue 2116](https://cplusplus.github.io/LWG/issue2116).

### Example

{/* source:cpp-types-is-constructible:0010 */}
```cpp
#include <iostream>
#include <type_traits>
 
class Foo
{
    int v1;
    double v2;
public:
    Foo(int n) : v1(n), v2() {}
    Foo(int n, double f) noexcept : v1(n), v2(f) {}
};
 
int main()
{
    auto is = [](bool o) { return (o ? "\t" "is " : "\t" "isn't "); };
    std::cout << "Foo ...\n"
              << is(std::is_trivially_constructible_v<Foo, const Foo&>)
              << "Trivially-constructible from const Foo&\n"
              << is(std::is_trivially_constructible_v<Foo, int>)
              << "Trivially-constructible from int\n"
              << is(std::is_constructible_v<Foo, int>)
              << "Constructible from int\n"
              << is(std::is_nothrow_constructible_v<Foo, int>)
              << "Nothrow-constructible from int\n"
              << is(std::is_nothrow_constructible_v<Foo, int, double>)
              << "Nothrow-constructible from int and double\n";
}
```

Output:

```text
Foo ...
        is Trivially-constructible from const Foo&
        isn't Trivially-constructible from int
        is Constructible from int
        isn't Nothrow-constructible from int
        is Nothrow-constructible from int and double
```
