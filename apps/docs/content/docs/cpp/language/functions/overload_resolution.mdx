{/* source:cpp-language-overload-resolution:0000 */}
In order to compile a function call, the compiler must first perform [name lookup](/docs/cpp/language/basic_concepts/lookup), which, for functions, may involve [argument-dependent lookup](/docs/cpp/language/functions/adl), and for function templates may be followed by [template argument deduction](/docs/cpp/language/templates/template_argument_deduction).

{/* source:cpp-language-overload-resolution:0001 */}
If the name refers to more than one entity, it is said to be *overloaded*, and the compiler must determine which overload to call. In simple terms, the overload whose parameters match the arguments most closely is the one that is called.

{/* source:cpp-language-overload-resolution:0002 */}
In detail, overload resolution proceeds through the following steps:

{/* source:cpp-language-overload-resolution:0003 */}
1. Building the set of [candidate functions](/docs/cpp/language/functions/overload_resolution#Candidate_functions).
2. Trimming the set to only [viable functions](/docs/cpp/language/functions/overload_resolution#Viable_functions).
3. Analyzing the set to determine the single [best viable function](/docs/cpp/language/functions/overload_resolution#Best_viable_function) (this may involve [ranking of implicit conversion sequences](/docs/cpp/language/functions/overload_resolution#Ranking_of_implicit_conversion_sequences)).

{/* source:cpp-language-overload-resolution:0004 */}
```cpp
void f(long);
void f(float);

f(0L); // calls f(long)
f(0);  // error: ambiguous overload
```

{/* source:cpp-language-overload-resolution:0005 */}
Besides function calls, overloaded function names may appear in several additional contexts, where different rules apply: see [Address of an overloaded function](/docs/cpp/language/functions/overloaded_address).

{/* source:cpp-language-overload-resolution:0006 */}
If a function cannot be selected by overload resolution, it cannot be used (e.g. it is a [templated entity](/docs/cpp/language/templates#Templated_entity) with a failed [constraint](/docs/cpp/language/templates/constraints)).

## Candidate functions

{/* source:cpp-language-overload-resolution:0007 */}
Before overload resolution begins, the functions selected by name lookup and template argument deduction are combined to form the set of candidate functions. The exact details depend on the context in which overload resolution will take place.

### Call to a named function

{/* source:cpp-language-overload-resolution:0008 */}
If `E` in a [function call expression](/docs/cpp/language/expressions/operator_other#Built-in_function_call_operator) `E(args)` names a set of overloaded functions and/or function templates (but not callable objects), the following rules are followed:

{/* source:cpp-language-overload-resolution:0009 */}
- If the expression `E` has the form `PA->B` or `A.B` (where `A` has class type cv `T`), then `B` is [looked up](/docs/cpp/language/basic_concepts/lookup) as a member function of `T`. The function declarations found by that lookup are the candidate functions. The argument list for the purpose of overload resolution has the implied object argument of type cv `T`.
- If the expression `E` is a [primary expression](/docs/cpp/language/expressions#Primary_expressions), the name is [looked up](/docs/cpp/language/basic_concepts/lookup) following normal rules for function calls (which may involve [ADL](/docs/cpp/language/functions/adl)). The function declarations found by this lookup are (due to the way lookup works) either:

{/* source:cpp-language-overload-resolution:0010 */}
- all non-member functions (in which case the argument list for the purpose of overload resolution is exactly the argument list used in the function call expression)
- all member functions of some class `T`, in which case, if `this` is in scope and is a pointer to `T` or to a derived class of `T`, `*this` is used as the implied object argument. Otherwise (if `this` is not in scope or does not point to `T`), a fake object of type `T` is used as the implied object argument, and if overload resolution subsequently selects a non-static member function, the program is ill-formed.

### Call to a class object

{/* source:cpp-language-overload-resolution:0011 */}
If `E` in a [function call expression](/docs/cpp/language/expressions/operator_other#Built-in_function_call_operator) `E(args)` has class type cv `T`, then

{/* source:cpp-language-overload-resolution:0012 */}
- The function-call operators of `T` are obtained by ordinary [lookup](/docs/cpp/language/basic_concepts/lookup) of the name `operator()` in the context of the expression `(E).operator()`, and every declaration found is added to the set of candidate functions.
- For each non-[explicit](/docs/cpp/language/classes/explicit) [user-defined conversion function](/docs/cpp/language/expressions/cast_operator) in `T` or in a base of `T` (unless hidden), whose cv-qualifiers are the same or greater than `T`'s cv-qualifiers, and where the conversion function converts to:

{/* source:cpp-language-overload-resolution:0013 */}
- pointer-to-function
- reference-to-pointer-to-function
- reference-to-function

then a *surrogate call function* with a unique name whose first parameter is the result of the conversion, the remaining parameters are the parameter list accepted by the result of the conversion, and the return type is the return type of the result of the conversion, is added to the set of candidate functions. If this surrogate function is selected by the subsequent overload resolution, then the user-defined conversion function will be called and then the result of the conversion will be called.

{/* source:cpp-language-overload-resolution:0014 */}
In any case, the argument list for the purpose of overload resolution is the argument list of the function call expression preceded by the implied object argument `E` (when matching against the surrogate function, the user-defined conversion will automatically convert the implied object argument to the first argument of the surrogate function).

{/* source:cpp-language-overload-resolution:0015 */}
```cpp
int f1(int);
int f2(float);

struct A
{
    using fp1 = int(*)(int);
    operator fp1() { return f1; } // conversion function to pointer to function
    using fp2 = int(*)(float);
    operator fp2() { return f2; } // conversion function to pointer to function
} a;

int i = a(1); // calls f1 via pointer returned from conversion function
```

### Call to an overloaded operator

{/* source:cpp-language-overload-resolution:0016 */}
If at least one of the arguments to an operator in an expression has a class type or an enumeration type, both [builtin operators](/docs/cpp/language/expressions#Operators) and [user-defined operator overloads](/docs/cpp/language/expressions/operators) participate in overload resolution, with the set of candidate functions selected as follows:

{/* source:cpp-language-overload-resolution:0017 */}
For a unary operator `@` whose argument has type `T1` (after removing cv-qualifications), or binary operator `@` whose left operand has type `T1` and right operand of type `T2` (after removing cv-qualifications), the following sets of candidate functions are prepared:

{/* source:cpp-language-overload-resolution:0018 */}
1) *member candidates*: if `T1` is a complete class or a class currently being defined, the set of member candidates is the result of [qualified name lookup](/docs/cpp/language/basic_concepts/lookup) of `T1::operator@`. In all other cases, the set of member candidates is empty.

{/* source:cpp-language-overload-resolution:0019 */}
2) *non-member candidates*: For the operators where [operator overloading](/docs/cpp/language/expressions/operators) permits non-member forms, all declarations found by [unqualified name lookup](/docs/cpp/language/basic_concepts/lookup) of `operator@` in the context of the expression (which may involve [ADL](/docs/cpp/language/functions/adl)), except that member function declarations are ignored and do not prevent the lookup from continuing into the next enclosing scope. If both operands of a binary operator or the only operand of a unary operator has enumeration type, the only functions from the lookup set that become non-member candidates are the ones whose parameter has that enumeration type (or reference to that enumeration type)

{/* source:cpp-language-overload-resolution:0020 */}
3) *built-in candidates*: For `operator,`, the unary `operator&`, and `operator->`, the set of built-in candidates is empty. For other operators built-in candidates are the ones listed in [built-in operator pages](/docs/cpp/language/expressions#Operators) as long as all operands can be implicitly converted to their parameters. If any built-in candidate has the same parameter list as a non-member candidate<InlineRevision since="C++20"> or rewritten non-member candidate</InlineRevision> that is not a function template specialization, it is not added to the list of built-in candidates. When the built-in assignment operators are considered, the conversions from their first parameters are restricted: only the [standard conversion sequences](/docs/cpp/language/expressions/implicit_cast) are considered.

{/* source:cpp-language-overload-resolution:0021 */}
<Revision since="C++20">
4) *rewritten candidates*:

- For the four relational operator expressions `x < y`, `x <= y`, `x > y`, and `x >= y`, all member, non-member, and built-in `operator<=>`s found are added to the set.
- For the four relational operator expressions `x < y`, `x <= y`, `x > y`, and `x >= y` as well as the three-way comparison expression `x <=> y`, a synthesized candidate with the order of the two parameters reversed is added for each member, non-member, and built-in `operator<=>`s found.
- For `x != y`, all member, non-member, and built-in `operator==`s found are added to the set, unless there is a matching `operator!=`.
- For equality operator expressions `x == y` and `x != y`, a synthesized candidate with the order of the two parameters reversed is added for each member, non-member, and built-in `operator==`s found, unless there is a matching `operator!=`.

In all cases, rewritten candidates are not considered in the context of the rewritten expression. For all other operators, the rewritten candidate set is empty.
</Revision>

{/* source:cpp-language-overload-resolution:0022 */}
The set of candidate functions to be submitted for overload resolution is a union of the sets above. The argument list for the purpose of overload resolution consists of the operands of the operator except for `operator->`, where the second operand is not an argument for the function call (see [member access operator](/docs/cpp/language/expressions/operator_member_access#Built-in_member_access_operators)).

{/* source:cpp-language-overload-resolution:0023 */}
```cpp
struct A
{
    operator int();              // user-defined conversion
};
A operator+(const A&, const A&); // non-member user-defined operator

void m()
{
    A a, b;
    a + b; // member-candidates: none
           // non-member candidates: operator+(a, b)
           // built-in candidates: int(a) + int(b)
           // overload resolution chooses operator+(a, b)
}
```

{/* source:cpp-language-overload-resolution:0024 */}
If the overload resolution selects a built-in candidate, the [user-defined conversion sequence](/docs/cpp/language/expressions/implicit_cast) from an operand of class type is not allowed to have a second standard conversion sequence: the user-defined conversion function must give the expected operand type directly:

{/* source:cpp-language-overload-resolution:0025 */}
```cpp
struct Y { operator int*(); }; // Y is convertible to int*
int *a = Y() + 100.0;          // error: no operator+ between pointer and double
```

{/* source:cpp-language-overload-resolution:0026 */}
For `operator,`, the unary `operator&`, and `operator->`, if there are no viable functions (see below) in the set of candidate functions, then the operator is reinterpreted as a built-in.

{/* source:cpp-language-overload-resolution:0027 */}
<Revision since="C++20">
If a rewritten `operator<=>` candidate is selected by overload resolution for an operator `@`, `x @ y` is interpreted as the rewritten expression: `0 @ (y <=> x)` if the selected candidate is a synthesized candidate with reversed order of parameters, or `(x <=> y) @ 0` otherwise, using the selected rewritten `operator<=>` candidate. If a rewritten `operator==` candidate is selected by overload resolution for an operator `@` (which is either `==` or `!=`), its return type must be (possibly cv-qualified) `bool`, and `x @ y` is interpreted as the rewritten expression: `y == x` or `!(y == x)` if the selected candidate is a synthesized candidate with reversed order of parameters, or `!(x == y)` otherwise, using the selected rewritten `operator==` candidate. Overload resolution in this case has a final tiebreaker preferring non-rewritten candidates to rewritten candidates, and preferring non-synthesized rewritten candidates to synthesized rewritten candidates. This lookup with the reversed arguments order makes it possible to write just `operator<=>(std::string, const char*)` and `operator==(std::string, const char*)` to generate all comparisons between [`std::string`](/docs/cpp/library/string/basic_string) and `const char*`, both ways. See [default comparisons](/docs/cpp/language/expressions/default_comparisons) for more detail.
</Revision>

### Initialization by constructor

{/* source:cpp-language-overload-resolution:0028 */}
When an object of class type is [direct-initialized](/docs/cpp/language/initialization/direct_initialization) or [default-initialized](/docs/cpp/language/initialization/default_initialization)<InlineRevision since="C++11"> (including default-initialization in the context of [copy-list-initialization](/docs/cpp/language/initialization/list_initialization))</InlineRevision>, the candidate functions are all constructors of the class being initialized. The argument list is the expression list of the initializer.

{/* source:cpp-language-overload-resolution:0029 */}
Otherwise, the candidate functions are all [converting constructors](/docs/cpp/language/classes/converting_constructor) of the class being initialized. The argument list is the expression of the initializer.

{/* source:cpp-language-overload-resolution:0030 */}
<Revision since="C++11">
For default-initialization in the context of copy-list-initialization, if an [explicit](/docs/cpp/language/classes/explicit) constructor is chosen, the initialization is ill-formed.
</Revision>

### Copy-initialization by conversion

{/* source:cpp-language-overload-resolution:0031 */}
If [copy-initialization](/docs/cpp/language/initialization/copy_initialization) of an object of class type requires that a user-defined conversion is called to convert the initializer expression of type cv `S` to the type cv `T` of the object being initialized, the following functions are candidate functions:

{/* source:cpp-language-overload-resolution:0032 */}
- all [converting constructors](/docs/cpp/language/classes/converting_constructor) of `T`
- the non-[explicit](/docs/cpp/language/classes/explicit) conversion functions from `S` and its base classes (unless hidden) to `T` or class derived from `T` or a reference to such. If this copy-initialization is part of the direct-initialization sequence of cv `T` (initializing a reference to be bound to the first parameter of a constructor that takes a reference to cv `T`), then explicit conversion functions are also considered.

{/* source:cpp-language-overload-resolution:0033 */}
Either way, the argument list for the purpose of overload resolution consists of a single argument which is the initializer expression, which will be compared against the first argument of the constructor or against the implicit object argument of the conversion function.

### Non-class initialization by conversion

{/* source:cpp-language-overload-resolution:0034 */}
When initialization of an object of non-class type cv1 `T` requires a [user-defined conversion function](/docs/cpp/language/expressions/cast_operator) to convert from an initializer expression of class type cv `S`, the following functions are candidates:

{/* source:cpp-language-overload-resolution:0035 */}
- the non-explicit user-defined conversion functions of `S` and its base classes (unless hidden) that produce type `T` or a type convertible to `T` by a [standard conversion sequence](/docs/cpp/language/expressions/implicit_cast), or a reference to such type. cv-qualifiers on the returned type are ignored for the purpose of selecting candidate functions.
- if this is [direct-initialization](/docs/cpp/language/initialization/direct_initialization), the explicit user-defined conversion functions of `S` and its base classes (unless hidden) that produce type `T` or a type convertible to `T` by a [qualification conversion](/docs/cpp/language/expressions/implicit_cast#Qualification_conversion), or a reference to such type, are also considered.

{/* source:cpp-language-overload-resolution:0036 */}
Either way, the argument list for the purpose of overload resolution consists of a single argument which is the initializer expression, which will be compared against the implicit object argument of the conversion function.

### Reference initialization by conversion

{/* source:cpp-language-overload-resolution:0037 */}
During [reference initialization](/docs/cpp/language/initialization/reference_initialization), where the reference to cv1 `T` is bound to the lvalue or rvalue result of a conversion from the initializer expression from the class type cv2 `S`, the following functions are selected for the candidate set:

{/* source:cpp-language-overload-resolution:0038 */}
The non-explicit user-defined conversion functions of `S` and its base classes (unless hidden) to the type

{/* source:cpp-language-overload-resolution:0039 */}
- (when converting to an lvalue) lvalue reference to cv2 `T2`
- (when converting to an rvalue or an lvalue of function type) cv2 `T2` or rvalue reference to cv2 `T2`

where cv2 `T2` is [reference-compatible](/docs/cpp/language/initialization/reference_initialization#Definitions) with cv1 `T`.

{/* source:cpp-language-overload-resolution:0040 */}
For direct initialization, the explicit user-defined conversion functions are also considered if `T2` is the same type as `T` or can be converted to type `T` with a qualification conversion.

{/* source:cpp-language-overload-resolution:0041 */}
Either way, the argument list for the purpose of overload resolution consists of a single argument which is the initializer expression, which will be compared against the implicit object argument of the conversion function.

### List-initialization

{/* source:cpp-language-overload-resolution:0042 */}
When an object of non-aggregate class type `T` is [list-initialized](/docs/cpp/language/initialization/list_initialization), two-phase overload resolution takes place.

{/* source:cpp-language-overload-resolution:0043 */}
- at phase 1, the candidate functions are all initializer-list constructors of `T` and the argument list for the purpose of overload resolution consists of a single initializer list argument
- if overload resolution fails at phase 1, phase 2 is entered, where the candidate functions are all constructors of `T` and the argument list for the purpose of overload resolution consists of the individual elements of the initializer list.

{/* source:cpp-language-overload-resolution:0044 */}
If the initializer list is empty and `T` has a default constructor, phase 1 is skipped.

{/* source:cpp-language-overload-resolution:0045 */}
In copy-list-initialization, if phase 2 selects an explicit constructor, the initialization is ill-formed (as opposed to all over copy-initializations where explicit constructors are not even considered).

### Additional rules for function template candidates

{/* source:cpp-language-overload-resolution:0046 */}
If name lookup found a function template, [template argument deduction](/docs/cpp/language/templates/template_argument_deduction) and checking of any explicit template arguments are performed to find the template argument values (if any) that can be used in this case:

{/* source:cpp-language-overload-resolution:0047 */}
- If both succeeds, the template arguments are used to synthesize declarations of the corresponding function template specializations, which are added to the candidate set, and such specializations are treated just like non-template functions except where specified otherwise in the tie-breaker rules below.
- If argument deduction fails or the synthesized function template specialization would be ill-formed, no such function is added to the candidate set (see [SFINAE](/docs/cpp/language/templates/sfinae)).

{/* source:cpp-language-overload-resolution:0048 */}
If a name refers to one or more function templates and also to a set of overloaded non-template functions, those functions and the specializations generated from the templates are all candidates.

{/* source:cpp-language-overload-resolution:0049 */}
See [function template overloading](/docs/cpp/language/templates/function_template#Function_template_overloading) for further detail.

{/* source:cpp-language-overload-resolution:0050 */}
<Revision since="C++20">
If a constructor template or conversion function template has a [conditional explicit specifier](/docs/cpp/language/classes/explicit) which happens to be [value-dependent](/docs/cpp/language/templates/dependent_name#Value-dependent_expressions), after deduction, if the context requires a candidate that is not explicit and the generated specialization is explicit, it is removed from the candidate set.
</Revision>

### Additional rules for constructor candidates

{/* source:cpp-language-overload-resolution:0051 */}
<Revision since="C++11">
Defaulted [move constructors](/docs/cpp/language/classes/move_constructor) and [move assignment operators](/docs/cpp/language/classes/move_operator) that are defined as deleted are excluded in the set of candidate functions.

A constructor [inherited](/docs/cpp/language/classes/using_declaration#Inheriting_constructors) from class type `C` that has a first parameter of type "reference to `P`" (including such a constructor instantiated from a template) is excluded from the set of candidate functions when constructing an object of type `D` if all following conditions are satisfied:

- The argument list has exactly one argument.
- `C` is [reference-related](/docs/cpp/language/initialization/reference_initialization#Definitions) to `P`.
- `P` is reference-related to `D`.
</Revision>

### Additional rules for member function candidates

{/* source:cpp-language-overload-resolution:0052 */}
If any candidate function is a [member function](/docs/cpp/language/classes/member_functions) (static or non-static)<InlineRevision since="C++23"> that does not have an [explicit object parameter](/docs/cpp/language/classes/member_functions#Explicit_object_parameter)</InlineRevision>, but not a constructor, it is treated as if it has an extra parameter (implicit object parameter) which represents the object for which they are called and appears before the first of the actual parameters.

{/* source:cpp-language-overload-resolution:0053 */}
Similarly, the object on which a member function is being called is prepended to the argument list as the implied object argument.

{/* source:cpp-language-overload-resolution:0054 */}
For member functions of class `X`, the type of the implicit object parameter is affected by cv-qualifications and ref-qualifications of the member function as described in [member functions](/docs/cpp/language/classes/member_functions).

{/* source:cpp-language-overload-resolution:0055 */}
The user-defined conversion functions are considered to be members of the implied object argument for the purpose of determining the type of the implicit object parameter.

{/* source:cpp-language-overload-resolution:0056 */}
The member functions introduced by a using-declaration into a derived class are considered to be members of the derived class for the purpose of defining the type of the implicit object parameter.

{/* source:cpp-language-overload-resolution:0057 */}
<Revision until="C++23">
For the static member functions, the implicit object parameter is considered to match any object: its type is not examined and no conversion sequence is attempted for it.
</Revision>

{/* source:cpp-language-overload-resolution:0058 */}
For the rest of overload resolution, the implied object argument is indistinguishable from other arguments, but the following special rules apply to the implicit object parameter:

{/* source:cpp-language-overload-resolution:0059 */}
1) user-defined conversions cannot be applied to the implicit object parameter

{/* source:cpp-language-overload-resolution:0060 */}
2) rvalues can be bound to non-const implicit object parameter <InlineRevision since="C++11">(unless this is for a ref-qualified member function)</InlineRevision> and do not affect the ranking of the implicit conversions.

```cpp
struct B { void f(int); };
struct A { operator B&(); };

A a;
a.B::f(1); // Error: user-defined conversions cannot be applied
           // to the implicit object parameter
static_cast<B&>(a).f(1); // OK
```

## Viable functions

{/* source:cpp-language-overload-resolution:0061 */}
Given the set of candidate functions, constructed as described above, the next step of overload resolution is examining arguments and parameters to reduce the set to the set of viable functions

{/* source:cpp-language-overload-resolution:0062 */}
To be included in the set of viable functions, the candidate function must satisfy the following:

{/* source:cpp-language-overload-resolution:0063 */}
1) If there are M arguments, the candidate function that has exactly M parameters is viable

{/* source:cpp-language-overload-resolution:0064 */}
2) If the candidate function has less than M parameters, but has an [ellipsis parameter](/docs/cpp/language/functions/variadic_arguments), it is viable.

{/* source:cpp-language-overload-resolution:0065 */}
3) If the candidate function has more than M parameters and the M+1'st parameter and all parameters that follow have default arguments, it is viable. For the rest of overload resolution, the parameter list is truncated at M.

{/* source:cpp-language-overload-resolution:0066 */}
<Revision since="C++20">
4) If the function has an associated [constraint](/docs/cpp/language/templates/constraints), it must be satisfied
</Revision>

{/* source:cpp-language-overload-resolution:0067 */}
5) For every argument there must be at least one implicit conversion sequence that converts it to the corresponding parameter.

{/* source:cpp-language-overload-resolution:0068 */}
6) If any parameter has reference type, reference binding is accounted for at this step: if an rvalue argument corresponds to non-const lvalue reference parameter or an lvalue argument corresponds to rvalue reference parameter, the function is not viable.

{/* source:cpp-language-overload-resolution:0069 */}
User-defined conversions (both converting constructors and user-defined conversion functions) are prohibited from taking part in implicit conversion sequence where it would make it possible to apply more than one user-defined conversion. Specifically, they are not considered if the target of the conversion is the first parameter of a constructor or the implicit object parameter of a user-defined conversion function, and that constructor/user-defined conversion is a candidate for

{/* source:cpp-language-overload-resolution:0070 */}
- [copy-initialization of a class by user-defined conversion](/docs/cpp/language/functions/overload_resolution#Copy-initialization_by_conversion),
- [initialization of a non-class type by a conversion function](/docs/cpp/language/functions/overload_resolution#Non-class_initialization_by_conversion),
- [initialization by conversion function for direct reference binding](/docs/cpp/language/functions/overload_resolution#Reference_initialization_by_conversion),
- [initialization by constructor](/docs/cpp/language/functions/overload_resolution#Initialization_by_constructor) during the second (direct-initialization) step of class [copy-initialization](/docs/cpp/language/initialization/copy_initialization),

{/* source:cpp-language-overload-resolution:0071 */}
<Revision since="C++11">
- initialization by list-initialization where the initializer list has exactly one element that is itself an initializer list, and the target is the first parameter of a constructor of class `X`, and the conversion is to `X` or reference to (possibly cv-qualified) `X`:

```cpp
struct A { A(int); };
struct B { B(A); };

B b{{0}}; // list-initialization of B

// candidates: B(const B&), B(B&&), B(A)
// {0} -> B&& not viable: would have to call B(A)
// {0} -> const B&: not viable: would have to bind to rvalue, would have to call B(A)
// {0} -> A viable. Calls A(int): user-defined conversion to A is not banned
```
</Revision>

## Best viable function

{/* source:cpp-language-overload-resolution:0072 */}
For each pair of viable function F1 and F2, the implicit conversion sequences from the i-th argument to i-th parameter are ranked to determine which one is better (except the first argument, the implicit object argument for static member functions has no effect on the ranking)

{/* source:cpp-language-overload-resolution:0073 */}
F1 is determined to be a better function than F2 if implicit conversions for all arguments of F1 are not worse than the implicit conversions for all arguments of F2, and

{/* source:cpp-language-overload-resolution:0074 */}
1) there is at least one argument of F1 whose implicit conversion is better than the corresponding implicit conversion for that argument of F2, or, if not that,

{/* source:cpp-language-overload-resolution:0075 */}
2) (only in context of non-class initialization by conversion), the standard conversion sequence from the result of F1 to the type being initialized is better than the standard conversion sequence from the result of F2, or, if not that,

{/* source:cpp-language-overload-resolution:0076 */}
<Revision since="C++11">
3) (only in context of initialization by conversion function for direct reference binding of a reference to function type), the result of F1 is the same kind of reference (lvalue or rvalue) as the reference being initialized, and the result of F2 is not, or, if not that,
</Revision>

{/* source:cpp-language-overload-resolution:0077 */}
4) F1 is a non-template function while F2 is a template specialization, or, if not that,

{/* source:cpp-language-overload-resolution:0078 */}
5) F1 and F2 are both template specializations and F1 is more specialized according to the [partial ordering rules for template specializations](/docs/cpp/language/templates/function_template#Function_template_overloading), or, if not that,

{/* source:cpp-language-overload-resolution:0079 */}
<Revision since="C++20">
6) F1 and F2 are non-template functions and F1 is [more partial-ordering-constrained](/docs/cpp/language/templates/constraints#Partial_ordering_of_constraints) than F2:

```cpp
template<typename T = int>
struct S
{
    constexpr void f(); // #1
    constexpr void f(this S&) requires true; // #2
};

void test()
{
    S<> s;
    s.f(); // calls #2
}
```

, or, if not that,
</Revision>

{/* source:cpp-language-overload-resolution:0080 */}
<Revision since="C++11">
7) F1 is a constructor for a class D, F2 is a constructor for a base class B of D, and for all arguments the corresponding parameters of F1 and F2 have the same type:

```cpp
struct A
{
    A(int = 0);
};

struct B: A
{
    using A::A;

    B();
};

B b; // OK, B::B()
```

, or, if not that,
</Revision>

{/* source:cpp-language-overload-resolution:0081 */}
<Revision since="C++20">
8) F2 is a rewritten candidate and F1 is not, or, if not that,
9) F1 and F2 are both rewritten candidates, and F2 is a synthesized rewritten candidate with reversed order of parameters and F1 is not, or, if not that,
</Revision>

{/* source:cpp-language-overload-resolution:0082 */}
<Revision since="C++17">
10) F1 is generated from a [user-defined deduction guide](/docs/cpp/language/templates/deduction_guide) and F2 is not, or, if not that,
11) F1 is the [copy deduction candidate](/docs/cpp/language/templates/deduction_guide) and F2 is not, or, if not that,
12) F1 is generated from a non-template constructor and F2 is generated from a constructor template:

```cpp
template<class T>
struct A
{
    using value_type = T;
    A(value_type);  // #1
    A(const A&);    // #2
    A(T, T, int);   // #3

    template<class U>
    A(int, T, U);   // #4
};                  // #5 is A(A), the copy deduction candidate

A x(1, 2, 3); // uses #3, generated from a non-template constructor

template<class T>
A(T) -> A<T>;       // #6, less specialized than #5

A a (42); // uses #6 to deduce A<int> and #1 to initialize
A b = a;  // uses #5 to deduce A<int> and #2 to initialize

template<class T>
A(A<T>) -> A<A<T>>; // #7, as specialized as #5
A b2 = a; // uses #7 to deduce A<A<int>> and #1 to initialize
```
</Revision>

{/* source:cpp-language-overload-resolution:0083 */}
These pair-wise comparisons are applied to all viable functions. If exactly one viable function is better than all others, overload resolution succeeds and this function is called. Otherwise, compilation fails.

{/* source:cpp-language-overload-resolution:0084 */}
```cpp
void Fcn(const int*, short); // overload #1
void Fcn(int*, int);         // overload #2

int i;
short s = 0;

void f() 
{
    Fcn(&i, 1L);  // 1st argument: &i -> int* is better than &i -> const int*
                  // 2nd argument: 1L -> short and 1L -> int are equivalent
                  // calls Fcn(int*, int)

    Fcn(&i, 'c'); // 1st argument: &i -> int* is better than &i -> const int*
                  // 2nd argument: 'c' -> int is better than 'c' -> short
                  // calls Fcn(int*, int)

    Fcn(&i, s);   // 1st argument: &i -> int* is better than &i -> const int*
                  // 2nd argument: s -> short is better than s -> int
                  // no winner, compilation error
}
```

{/* source:cpp-language-overload-resolution:0085 */}
If the best viable function resolves to a function for which multiple declarations were found, and if any two of these declarations inhabit different scopes and specify a default argument that made the function viable, the program is ill-formed.

{/* source:cpp-language-overload-resolution:0086 */}
```cpp
namespace A
{
    extern "C" void f(int = 5);
}

namespace B
{
    extern "C" void f(int = 5);
}

using A::f;
using B::f;

void use()
{
    f(3); // OK, default argument was not used for viability
    f();  // error: found default argument twice
}
```

## Ranking of implicit conversion sequences

{/* source:cpp-language-overload-resolution:0087 */}
The argument-parameter implicit conversion sequences considered by overload resolution correspond to [implicit conversions](/docs/cpp/language/expressions/implicit_cast) used in [copy initialization](/docs/cpp/language/initialization/copy_initialization) (for non-reference parameters), except that when considering conversion to the implicit object parameter or to the left-hand side of assignment operator, conversions that create temporary objects are not considered. <InlineRevision since="C++23">When the parameter is the implicit object parameter of a static member function, the implicit conversion sequence is a standard conversion sequence that is neither better nor worse than any other standard conversion sequence.</InlineRevision>

{/* source:cpp-language-overload-resolution:0088 */}
Each [type of standard conversion sequence](/docs/cpp/language/expressions/implicit_cast) is assigned one of three ranks:

{/* source:cpp-language-overload-resolution:0089 */}
1) Exact Match: no conversion required, lvalue-to-rvalue conversion, qualification conversion, <InlineRevision since="C++17">function pointer conversion,</InlineRevision> user-defined conversion of class type to the same class

{/* source:cpp-language-overload-resolution:0090 */}
2) Promotion: integral promotion, floating-point promotion

{/* source:cpp-language-overload-resolution:0091 */}
3) Conversion: integral conversion, floating-point conversion, floating-integral conversion, pointer conversion, pointer-to-member conversion, boolean conversion, user-defined conversion of a derived class to its base

{/* source:cpp-language-overload-resolution:0092 */}
The rank of the standard conversion sequence is the worst of the ranks of the standard conversions it holds (there may be up to [three conversions](/docs/cpp/language/expressions/implicit_cast))

{/* source:cpp-language-overload-resolution:0093 */}
Binding of a reference parameter directly to the argument expression is either identity or a derived-to-base conversion:

{/* source:cpp-language-overload-resolution:0094 */}
```cpp
struct Base {};
struct Derived : Base {} d;

int f(Base&);    // overload #1
int f(Derived&); // overload #2

int i = f(d); // d -> Derived& has rank Exact Match
              // d -> Base& has rank Conversion
              // calls f(Derived&)
```

{/* source:cpp-language-overload-resolution:0095 */}
Since ranking of conversion sequences operates with types and value categories only, a [bit field](/docs/cpp/language/classes/bit_field) can bind to a reference argument for the purpose of ranking, but if that function gets selected, it will be ill-formed.

{/* source:cpp-language-overload-resolution:0096 */}
1) A standard conversion sequence is always better than a user-defined conversion sequence or an ellipsis conversion sequence.

{/* source:cpp-language-overload-resolution:0097 */}
2) A user-defined conversion sequence is always better than an [ellipsis conversion](/docs/cpp/language/functions/variadic_arguments) sequence.

{/* source:cpp-language-overload-resolution:0098 */}
3) A standard conversion sequence S1 is better than a standard conversion sequence S2 if

{/* source:cpp-language-overload-resolution:0099 */}
a) S1 is a proper subsequence of S2, excluding lvalue transformations; the identity conversion sequence is considered a subsequence of any non-identity conversion, or, if not that,

{/* source:cpp-language-overload-resolution:0100 */}
b) the rank of S1 is better than the rank of S2, or, if not that,

{/* source:cpp-language-overload-resolution:0101 */}
c) both S1 and S2 are binding to a reference parameter to something other than the implicit object parameter of a ref-qualified member function, and S1 binds an rvalue reference to an rvalue while S2 binds an lvalue reference to an rvalue:

```cpp
int i;
int f1();

int g(const int&);  // overload #1
int g(const int&&); // overload #2

int j = g(i);    // lvalue int -> const int& is the only valid conversion
int k = g(f1()); // rvalue int -> const int&& better than rvalue int -> const int&
```

{/* source:cpp-language-overload-resolution:0102 */}
or, if not that,

{/* source:cpp-language-overload-resolution:0103 */}
d) both S1 and S2 are binding to a reference parameter and S1 binds an lvalue reference to function while S2 binds an rvalue reference to function:

```cpp
int f(void(&)());  // overload #1
int f(void(&&)()); // overload #2

void g();
int i1 = f(g); // calls #1
```

{/* source:cpp-language-overload-resolution:0104 */}
or, if not that,

{/* source:cpp-language-overload-resolution:0105 */}
e) `S1` and `S2` only differ in qualification conversion, and

<Revision until="C++20">
the cv-qualification of the result of `S1` is a proper subset of the cv-qualification of the result of `S2`<InlineRevision until="C++11">, and `S1` is not the [deprecated string literal array-to-pointer conversion](/docs/cpp/language/expressions/string_literal#Notes)</InlineRevision>.
</Revision>

<Revision since="C++20">
the result of `S1` can be converted to the result of `S2` by a qualification conversion.
</Revision>

```cpp
int f(const int*);
int f(int*);

int i;
int j = f(&i); // &i -> int* is better than &i -> const int*, calls f(int*)
```

{/* source:cpp-language-overload-resolution:0106 */}
or, if not that,

{/* source:cpp-language-overload-resolution:0107 */}
f) both S1 and S2 are binding to a reference parameters only different in top-level cv-qualification, and S1's type is less cv-qualified than S2's:

```cpp
int f(const int &); // overload #1
int f(int &);       // overload #2 (both references)

int g(const int &); // overload #1
int g(int);         // overload #2

int i;
int j = f(i); // lvalue i -> int& is better than lvalue int -> const int&
              // calls f(int&)
int k = g(i); // lvalue i -> const int& ranks Exact Match
              // lvalue i -> rvalue int ranks Exact Match
              // ambiguous overload: compilation error
```

{/* source:cpp-language-overload-resolution:0108 */}
or, if not that,

{/* source:cpp-language-overload-resolution:0109 */}
g) S1 and S2 bind the same reference type “reference to T” and have source types V1 and V2, respectively, where the standard conversion sequence from V1* to T* is better than the standard conversion sequence from V2* to T*:

```cpp
struct Z {};

struct A
{
    operator Z&();
    operator const Z&();  // overload #1
};

struct B
{
    operator Z();
    operator const Z&&(); // overload #2
};

const Z& r1 = A();        // OK, uses #1
const Z&& r2 = B();       // OK, uses #2
```

{/* source:cpp-language-overload-resolution:0110 */}
4) A user-defined conversion sequence U1 is better than a user-defined conversion sequence U2 if they call the same constructor/user-defined conversion function or initialize the same class with aggregate-initialization, and in either case the second standard conversion sequence in U1 is better than the second standard conversion sequence in U2

```cpp
struct A
{
    operator short(); // user-defined conversion function
} a;

int f(int);   // overload #1
int f(float); // overload #2

int i = f(a); // A -> short, followed by short -> int (rank Promotion)
              // A -> short, followed by short -> float (rank Conversion)
              // calls f(int)
```

{/* source:cpp-language-overload-resolution:0111 */}
5) A list-initialization sequence L1 is better than list-initialization sequence L2 if L1 initializes an [`std::initializer_list`](/docs/cpp/library/utility/initializer_list) parameter, while L2 does not.

```cpp
void f1(int);                                 // #1
void f1(std::initializer_list<long>);         // #2
void g1() { f1({42}); }                       // chooses #2

void f2(std::pair<const char*, const char*>); // #3
void f2(std::initializer_list<std::string>);  // #4
void g2() { f2({"foo", "bar"}); }             // chooses #4
```

{/* source:cpp-language-overload-resolution:0112 */}
<Revision since="C++11" until="C++20">
6) A list-initialization sequence `L1` is *better* than list-initialization sequence `L2` if the corresponding parameters are references to arrays, and L1 converts to type "array of N1 T," L2 converts to type "array of N2 T", and N1 is smaller than N2.
</Revision>

<Revision since="C++20">
6) A list-initialization sequence `L1` is *better* than list-initialization sequence `L2` if the corresponding parameters are references to arrays, and L1 and L2 convert to arrays of same element type, and either
- the number of elements N1 initialized by L1 is less than the number of elements N2 initialized by L2, or
- N1 is equal to N2 and L2 converts to an array of unknown bound and L1 does not.

```cpp
void f(int    (&&)[] ); // overload #1
void f(double (&&)[] ); // overload #2
void f(int    (&&)[2]); // overload #3

f({1});        // #1: Better than #2 due to conversion, better than #3 due to bounds
f({1.0});      // #2: double -> double is better than double -> int
f({1.0, 2.0}); // #2: double -> double is better than double -> int
f({1, 2});     // #3: -> int[2] is better than -> int[], 
               //     and int -> int is better than int -> double
```
</Revision>

{/* source:cpp-language-overload-resolution:0113 */}
If two conversion sequences are indistinguishable because they have the same rank, the following additional rules apply:

{/* source:cpp-language-overload-resolution:0114 */}
1) Conversion that does not involve pointer to `bool` or pointer-to-member to `bool` is better than the one that does.

{/* source:cpp-language-overload-resolution:0115 */}
<Revision since="C++11">
2) Conversion that promotes an [enumeration](/docs/cpp/language/declarations/enum) whose underlying type is fixed to its underlying type is better than one that promotes to the promoted underlying type, if the two types are different.

```cpp
enum num : char { one = '0' };
std::cout << num::one; // '0', not 48
```
</Revision>

{/* source:cpp-language-overload-resolution:0116 */}
<Revision since="C++23">
3) A conversion in either direction between floating-point type `FP1` and floating-point type `FP2` is better than a conversion in the same direction between `FP1` and arithmetic type `T3` if
- the [floating-point conversion rank](/docs/cpp/language/expressions/usual_arithmetic_conversions#Floating-point_conversion_rank) of `FP1` is equal to the rank of `FP2`, and
  - `T3` is not a floating-point type, or
  - `T3` is a floating-point type whose rank is not equal to the rank of `FP1`, or
  - the [floating-point conversion subrank](/docs/cpp/language/expressions/usual_arithmetic_conversions#Floating-point_conversion_subrank) of `FP2` is greater than the subrank of `T3`.

```cpp
int f(std::float32_t);
int f(std::float64_t);
int f(long long);

float x;
std::float16_t y;

int i = f(x); // calls f(std::float32_t) on implementations where
              // float and std::float32_t have equal conversion ranks
int j = f(y); // error: ambiguous, no equal conversion rank
```
</Revision>

{/* source:cpp-language-overload-resolution:0117 */}
4) Conversion that converts pointer-to-derived to pointer-to-base is better than the conversion of pointer-to-derived to pointer-to-`void`, and conversion of pointer-to-base to `void` is better than pointer-to-derived to `void`.

{/* source:cpp-language-overload-resolution:0118 */}
5) If Mid is derived (directly or indirectly) from Base, and Derived is derived (directly or indirectly) from Mid

{/* source:cpp-language-overload-resolution:0119 */}
a) `Derived*` to `Mid*` is better than `Derived*` to `Base*`

{/* source:cpp-language-overload-resolution:0120 */}
b) `Derived` to `Mid&` or `Mid&&` is better than `Derived` to `Base&` or `Base&&`

{/* source:cpp-language-overload-resolution:0121 */}
c) `Base::*` to `Mid::*` is better than `Base::*` to `Derived::*`

{/* source:cpp-language-overload-resolution:0122 */}
d) `Derived` to `Mid` is better than `Derived` to `Base`

{/* source:cpp-language-overload-resolution:0123 */}
e) `Mid*` to `Base*` is better than `Derived*` to `Base*`

{/* source:cpp-language-overload-resolution:0124 */}
f) `Mid` to `Base&` or `Base&&` is better than `Derived` to `Base&` or `Base&&`

{/* source:cpp-language-overload-resolution:0125 */}
g) `Mid::*` to `Derived::*` is better than `Base::*` to `Derived::*`

{/* source:cpp-language-overload-resolution:0126 */}
h) `Mid` to `Base` is better than `Derived` to `Base`

{/* source:cpp-language-overload-resolution:0127 */}
Ambiguous conversion sequences are ranked as user-defined conversion sequences because multiple conversion sequences for an argument can exist only if they involve different user-defined conversions:

{/* source:cpp-language-overload-resolution:0128 */}
```cpp
class B;

class A { A (B&);};         // converting constructor
class B { operator A (); }; // user-defined conversion function
class C { C (B&); };        // converting constructor

void f(A) {} // overload #1
void f(C) {} // overload #2

B b;
f(b); // B -> A via ctor or B -> A via function (ambiguous conversion)
      // b -> C via ctor (user-defined conversion)
      // the conversions for overload #1 and for overload #2
      // are indistinguishable; compilation fails
```

## Implicit conversion sequence in list-initialization

{/* source:cpp-language-overload-resolution:0129 */}
In [list initialization](/docs/cpp/language/initialization/list_initialization), the argument is a braced-init-list, which isn't an expression, so the implicit conversion sequence into the parameter type for the purpose of overload resolution is decided by the following special rules:

{/* source:cpp-language-overload-resolution:0130 */}
- If the parameter type is some aggregate X and the initializer list consists of exactly one element of same or derived class (possibly cv-qualified), the implicit conversion sequence is the one required to convert the element to the parameter type.
- Otherwise, if the parameter type is a reference to character array and the initializer list has a single element that is an appropriately-typed string literal, the implicit conversion sequence is the identity conversion.
- Otherwise, if the parameter type is `std::initializer_list<X>`, and there is a non-narrowing implicit conversion from every element of the initializer list to X, the implicit conversion sequence for the purpose of overload resolution is the worst conversion necessary. If the braced-init-list is empty, the conversion sequence is the identity conversion.

{/* source:cpp-language-overload-resolution:0131 */}
```cpp
struct A
{
    A(std::initializer_list<double>);          // #1
    A(std::initializer_list<complex<double>>); // #2
    A(std::initializer_list<std::string>);     // #3
};
A a{1.0, 2.0};     // selects #1 (rvalue double -> double: identity conv)

void g(A);
g({"foo", "bar"}); // selects #3 (lvalue const char[4] -> std::string: user-def conv)
```

{/* source:cpp-language-overload-resolution:0132 */}
- Otherwise, if the parameter type is "array of N T" (this only happens for references to arrays), the initializer list must have N or less elements, and the worst implicit conversion necessary to convert every element of the list (or the empty pair of braces {} if the list is shorter than N) to T is the one used.

{/* source:cpp-language-overload-resolution:0133 */}
<Revision since="C++20">
- Otherwise, if the parameter type is "array of unknown bound of T" (this only happens for references to arrays), the worst implicit conversion necessary to convert every element of the list to `T` is the one used.
</Revision>

{/* source:cpp-language-overload-resolution:0134 */}
```cpp
typedef int IA[3];

void h(const IA&);
void g(int (&&)[]);

h({1, 2, 3}); // int->int identity conversion
g({1, 2, 3}); // same as above since C++20
```

{/* source:cpp-language-overload-resolution:0135 */}
- Otherwise, if the parameter type is a non-aggregate class type X, overload resolution picks the constructor C of X to initialize from the argument initializer list

{/* source:cpp-language-overload-resolution:0136 */}
- If C is not an initializer-list constructor and the initializer list has a single element of possibly cv-qualified X, the implicit conversion sequence has Exact Match rank.
- If the initializer list has a single element of possibly cv-qualified type derived from X, the implicit conversion sequence has Conversion rank. (note the difference from aggregates: aggregates initialize directly from single-element init lists before considering aggregate initialization, non-aggregates consider initializer_list constructors before any other constructors)
- otherwise, the implicit conversion sequence is a user-defined conversion sequence with the second standard conversion sequence an identity conversion.

{/* source:cpp-language-overload-resolution:0137 */}
If multiple constructors are viable but none is better than the others, the implicit conversion sequence is the ambiguous conversion sequence.

{/* source:cpp-language-overload-resolution:0138 */}
```cpp
struct A { A(std::initializer_list<int>); };
void f(A);

struct B { B(int, double); };
void g(B);

g({'a', 'b'});    // calls g(B(int, double)), user-defined conversion
// g({1.0, 1,0}); // error: double->int is narrowing, not allowed in list-init

void f(B);
// f({'a', 'b'}); // f(A) and f(B) both user-defined conversions
```

{/* source:cpp-language-overload-resolution:0139 */}
- Otherwise, if the parameter type is an aggregate which can be initialized from the initializer list according by [aggregate initialization](/docs/cpp/language/initialization/aggregate_initialization), the implicit conversion sequence is a user-defined conversion sequence with the second standard conversion sequence an identity conversion.

{/* source:cpp-language-overload-resolution:0140 */}
```cpp
struct A { int m1; double m2; };

void f(A);
f({'a', 'b'}); // calls f(A(int, double)), user-defined conversion
```

{/* source:cpp-language-overload-resolution:0141 */}
- Otherwise, if the parameter is a reference, reference initialization rules apply

{/* source:cpp-language-overload-resolution:0142 */}
```cpp
struct A { int m1; double m2; };

void f(const A&);
f({'a', 'b'}); // temporary created, f(A(int, double)) called. User-defined conversion
```

{/* source:cpp-language-overload-resolution:0143 */}
- Otherwise, if the parameter type is not a class and the initializer list has one element, the implicit conversion sequence is the one required to convert the element to the parameter type
- Otherwise, if the parameter type is not a class type and if the initializer list has no elements, the implicit conversion sequence is the identity conversion.

{/* source:cpp-language-overload-resolution:0144 */}
<Revision since="C++20">
If the argument is a designated initializer list and the parameter is not a reference, a conversion is only possible if the parameter has an aggregate type that can be initialized from that initializer list according to the rules for [aggregate initialization](/docs/cpp/language/initialization/aggregate_initialization), in which case the implicit conversion sequence is a user-defined conversion sequence whose second standard conversion sequence is an identity conversion. If, after overload resolution, the order of declaration of the aggregate's members does not match for the selected overload, the initialization of the parameter will be ill-formed.

```cpp
struct A { int x, y; };
struct B { int y, x; };

void f(A a, int); // #1
void f(B b, ...); // #2
void g(A a);      // #3
void g(B b);      // #4

void h() 
{
    f({.x = 1, .y = 2}, 0); // OK; calls #1
    f({.y = 2, .x = 1}, 0); // error: selects #1, initialization of a fails
                            // due to non-matching member order
    g({.x = 1, .y = 2});    // error: ambiguous between #3 and #4
}
```
</Revision>
